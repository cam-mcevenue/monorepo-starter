# Triage

Move issues through a small state machine of triage roles. Read the **use-issue-tracker** skill first: it holds the labels and their meanings, the commands, and how each outcome closes.

Every comment posted on an **external issue** (its author isn't the operator) **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs

## Roles

- **Type**: one of `bug`, `enhancement`, `documentation`. `spec` comes only from `/to-spec`, never from triage.
- **State**: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`.
- **Outcome**, when closing: `wontfix`, `duplicate`, `deferred`.

Every triaged open issue carries exactly one type and one state, plus its domain label when it belongs to a domain other than `codebase`. If state labels conflict, flag it and ask the operator before doing anything else.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or closes with an outcome. `needs-info` returns to `needs-triage` once the reporter replies. The operator can override at any time; flag transitions that look unusual and ask before proceeding. An external issue reaches `ready-for-agent` or `ready-for-human` only on the operator's direction in this session.

## Invocation

The operator invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the open issues and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

Show counts and a one-line summary per item. Let the operator pick.

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, labels, author, dates). Parse any prior triage notes so you don't re-ask resolved questions. Explore the issue's domain using its glossary, respecting ADRs in the area. Run two checks:
   - **Redundancy**: search for an existing implementation of the requested behavior by domain concept (not just the request's wording): the code for a codebase issue, the domain's docs and records for any other. Report where you looked. If found, it's an already-implemented `wontfix` (step 5).
   - **Prior requests**: list the titles of closed `wontfix` and `deferred` issues in the same domain (`gh issue list --state closed --label <outcome> --json number,title --limit 500`, once per outcome). Narrow it to the domain: add `--label domain:<name>` for a labelled domain; for `codebase`, which has no label, exclude every domain label listed in `ai-docs/ISSUE-TRACKER.md` with `--search '-label:"domain:<name>" ...'`. Read the list and match by concept, not wording: "night theme" matches "Dark mode theme". Open the matches for their reasons, and surface any that resembles this request.

2. **Recommend.** Tell the operator your type, domain, and state or outcome recommendation with reasoning, plus a brief summary of what you found (including whether it's already implemented, or matches a prior request). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a codebase bug, reproduce it from the reporter's steps; in any other domain, check the claim against the domain's docs and records. Report what happened: confirmed (with where), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, read the **grill-me** and **domain-modeling** skills, then follow both together to grill it into shape a round of questions at a time, sharpening domain terms and updating the glossary and ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - `needs-triage`: apply the role. Optional comment if there's partial progress.
   - Closing, each closed the way `use-issue-tracker` specifies:
     - **`wontfix`, already implemented**: the comment points to where it lives.
     - **`wontfix`, rejected**: the comment is an out-of-scope record (template below). When the rejection marks a lasting scope boundary ("we don't do theming"), also offer to record it as an ADR through `domain-modeling`, so the next request meets the decision.
     - **`deferred`**: the comment is an out-of-scope record, with its "Would reopen if" line.
     - **`duplicate`**: of the issue that already covers it. GitHub lists every duplicate on the original, so repeat requests group there.
     - **Matches a prior request**: a rejected one, once the operator confirms the decision still holds, closes the new issue as its `duplicate`. A deferred one is reopened (it returns to `needs-triage`) and the new issue closes as its `duplicate`, so the history stays on one issue.

   Before closing a `wontfix` or `deferred` issue, retitle it to name the concept in glossary terms (`gh issue edit <n> --title "Dark mode theme"`), so later prior-request checks can match it from the title alone.

## Quick state override

If the operator says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Out-of-scope record template

The closing comment on a rejected `wontfix` or a `deferred` issue: the durable record a later prior-request check reads.

```markdown
## Out of scope: <Concept>

**Decision:** <what won't be done, or won't be done yet>

**Why:** <the substantive reason: project scope, a constraint, a strategic choice>

**Would reopen if:** <deferred only: what would bring it back>
```

Write the reason to last: not "we don't want this" or "we're busy right now", but why the concept doesn't fit.

## Resuming a previous session

If prior triage notes exist on the issue, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
